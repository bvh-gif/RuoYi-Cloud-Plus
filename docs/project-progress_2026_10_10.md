# RuoYi-Cloud-Plus 工程化与 Agent Runtime 基础设施：项目进度

> 文档用途：团队共同维护的项目状态基线、任务看板补充说明与里程碑验收记录。  
> 整理日期：2026-10-10  
> 状态原则：本文件根据已有操作记录整理；历史上出现过的状态不等于当前仍然成立。凡未在当前环境重新验证的项目均明确标注“待复验”。

## 1. 项目目标与范围

### 1.1 总体目标

围绕现有 RuoYi-Cloud-Plus 开发环境，逐步建设可重复、可观测、可恢复的工程流水线：

**代码变更 → 自动触发 → 隔离构建 → 自动测试 → 生成制品/镜像 → 部署 → 状态与日志可追踪 → 失败可重试或恢复。**

- **近期价值：** 降低本地开发、调试、构建和部署的重复操作，缩短问题定位时间。
- **中期目标：** 将构建、测试、镜像和部署过程变成有明确输入、输出、退出码和验收标准的流水线。
- **长期目标：** 为 Agent 提供受权限控制的执行环境、可验证的执行循环、任务状态与检查点、可审计的工具调用以及失败恢复能力。

### 1.2 原则

1. 先验证当前实现，再决定是否重构；避免重复造轮子。
2. 先做到“可靠、可验证、可恢复”，再追求更复杂的自动化。
3. 一次只推进一个有验收标准的任务；完成后记录证据。
4. 不把容器 `Up`、脚本无报错或代码已提交等同于端到端完成。
5. 生产数据、安全凭据和原业务分支优先保护。

## 3. 进度状态定义

- **待规划：** 尚未拆成明确任务。
- **待实施：** 目标、范围和验收标准已定义，尚未实现。
- **进行中：** 正在实现或排查。
- **待验收：** 已实现或已有初步实现，但缺少完整验收证据。
- **已完成：** 验收标准全部通过，证据已记录。
- **阻塞：** 缺少依赖、权限、环境或决策，无法继续推进。
- **暂缓：** 已明确决定暂时不做，并记录原因。

不要用“差不多”“应该能用”作为状态。若只验证了正常路径，失败路径仍需测试时，应保持“待验收”。

## 5. 推荐里程碑

### M0：基线可复现
- 明确 Windows / WSL 实际仓库位置。
- 记录 Git 分支、远程、工作区与服务状态。
- 将当前 Makefile 和 Compose 文件的目标、输入和副作用记录下来。

### M1：基础服务可靠
- 服务 readiness 检查生效。
- 必需配置缺失时安全失败。
- 超时和错误码传播符合预期。
- 重复运行不会造成意外副作用。

### M2：构建与测试自动化
- 统一入口执行相关构建和测试。
- 保存测试报告、构建日志和产物信息。
- 将至少一种预期失败路径纳入验收。

### M3：发布可观测、可恢复
- 镜像和制品能关联源码提交。
- 部署后有明确健康验证。
- 部署失败时具备可执行的恢复或回滚步骤。

### M4：Agent Runtime 最小闭环
- 任务有状态机或明确状态转换。
- 工具调用受权限和执行环境限制。
- 可持久化执行记录与检查点。
- 对非幂等操作有去重、补偿或人工确认策略。
