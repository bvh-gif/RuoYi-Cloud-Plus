# RuoYi-Cloud-Plus 团队开发与协作规范

> 文档版本：v1.0  
> 整理日期：2026-10-10  
> 适用范围：项目代码、开发脚本、Docker/Compose、本地流水线及后续 Agent Runtime 工程。

## 1. 协作基本原则

1. **先检查，再修改。** 改动前记录当前分支、工作区状态、目标文件和影响范围。
2. **小步变更。** 一个 PR / 合并请求尽量解决一个问题，避免把功能、重构和格式化混在一起。
3. **可验证优先。** 每项功能先定义验收条件，再开始实现。
4. **安全默认。** 凭据不进 Git；危险操作不隐藏在普通开发命令中；服务使用最小必要权限。
5. **失败透明。** 不吞错误、不伪装成功；日志足以判断失败阶段和原因。
6. **可恢复优先。** 关键操作需要说明重试、幂等、补偿、备份或回滚策略。
7. **文档随代码更新。** 命令、配置、架构或行为变化时同步更新操作文档和验收记录。

## 2. Git 工作流

### 2.1 远程仓库约定

- `origin`：个人 Fork，正常推送目标。
- `upstream`：官方仓库，主要用于获取官方更新和对比变更。
- 除非获得明确授权，不向 `upstream` 推送。

### 2.2 分支约定

- `6.X`：现有业务分支；不要把基础设施实验直接混入该分支。
- `docs/project-progress`：进度、开发规范与决策文档分支。
- 新任务使用短期分支，例如：
  - `feat/mysql-readiness`
  - `feat/pipeline-runner`
  - `fix/compose-env-validation`
  - `docs/development-standards`

分支命名以前缀表达意图；不要在多个无关任务之间复用同一个长期功能分支。

### 2.3 提交规范

推荐格式：

```text
<type>: <简短描述>
```

建议类型：

- `feat`：新增功能
- `fix`：修复问题
- `docs`：文档
- `test`：测试
- `refactor`：不改变外部行为的重构
- `build`：构建或依赖管理
- `ci`：持续集成流水线
- `chore`：其他维护工作

提交示例：

```text
docs: add project development standards
fix: validate required mysql environment variables
feat: add mysql readiness check
```

提交标题要说明改动内容，不写“update”“改一下”“修复问题”等缺乏上下文的描述。

### 2.4 修改前与提交前检查

PowerShell 示例：

```powershell
# 确认仓库、分支和工作区
 git rev-parse --show-toplevel
 git branch --show-current
 git status --short --branch

# 查看当前差异
 git diff --stat
 git diff

# 检查空白错误
 git diff --check
```

提交前至少确认：

- 没有把密码、令牌、私钥、日志转储或本地临时文件加入提交。
- 修改范围与任务一致。
- 相关测试已执行，或明确注明未执行原因。
- 文档、配置样例和验收条件已同步。

推送前再次确认当前分支和远程目标。禁止在未审查工作区时执行 `git reset --hard`、强制推送、批量删除或清理命令。

## 3. 任务管理规范

每个任务至少包含：

- 唯一 ID 与任务标题。
- 背景 / 问题描述。
- 目标与非目标。
- 负责人或认领者。
- 优先级与依赖项。
- 实施范围及可能影响。
- 验收标准（尽可能可自动执行）。
- 测试命令、预期结果和实际结果。
- 风险、回滚 / 恢复方案。
- 当前状态与证据链接。

### 3.1 状态定义

`待规划 → 待实施 → 进行中 → 待验收 → 已完成`。  
遇到阻塞时可标为 `阻塞`；暂停的任务标为 `暂缓` 并写明原因。

“已完成”必须意味着验收标准通过并有证据。代码写完、容器启动、命令未报错都不单独构成完成标准。

### 3.2 任务拆分原则

- 单项任务应能在有限范围内独立实现和验证。
- 将“搭建完整流水线”拆成 readiness、build/test、制品、部署、可观测、恢复等子任务。
- 将正常流程与故障路径纳入同一验收计划。
- 如果任务扩大或验收条件变化，应更新描述并与相关协作者同步。

## 4. PowerShell、WSL 与运行环境

1. 命令块要注明执行环境：Windows PowerShell、WSL Bash 或容器内部。
2. 每次执行前确认仓库根目录与当前分支。项目历史里出现过多个 Windows / WSL 路径，必须先确认实际目标目录。
3. 避免将 Windows 路径直接传给 Linux 工具，或把 WSL 路径用于 Windows 原生命令而不做转换。
4. WSL 下关注文件权限、换行符、挂载路径、文件所有权和文件系统性能。
5. 自动化脚本需要说明必需工具、最低版本、必需环境变量和退出码语义。
6. 涉及删除、覆盖、清空数据库、清理卷的命令，先执行只读预览并确认目标。

## 5. Makefile 与脚本规范

### 5.1 统一入口

按实际需要逐步提供以下 Makefile 目标：

- `help`：列出目标、用途和必要参数。
- `status`：检查环境与服务状态，不产生破坏性副作用。
- `dev`：启动或确保本地开发依赖运行。
- `test`：运行约定测试。
- `build`：构建代码或制品。
- `deploy`：发布到明确指定的环境。
- `logs`：查看相关服务或流水线日志。
- `clean`：只清理明确列出的可再生成文件；默认不删数据卷。

不要把上面的示例目标视为当前全部已实现的事实；实施前先盘点已有 Makefile。

### 5.2 可靠性要求

- 检查依赖程序、配置文件、必要目录、环境变量和 Docker daemon。
- 所有失败路径应返回非零退出码；不能只打印错误后继续。
- 长耗时操作需有超时或取消策略。
- 等待服务使用有上限的轮询式 readiness，而不是只依赖固定 `sleep`。
- 重复执行同一目标应尽可能幂等，并说明不幂等的步骤。
- 失败输出应包含阶段、目标、相关日志位置和下一步排查提示。
- 对可能修改数据的目标，明确写出副作用并要求适当保护措施。

## 6. 配置、秘密与 Docker 安全

1. 使用 `.env.example` 或等效模板记录配置键和示例占位值；不提交真实 `.env` 或真实凭据。
2. 必需配置缺失时应明确失败，避免密码默认为空或静默套用不安全默认值。
3. 检查 `privileged: true`、`network_mode: host`、宿主机目录挂载和公开端口；每项都需有明确理由和最小权限边界。
4. 仅暴露必要端口，区分本地调试、局域网和公共网络访问。
5. 评估镜像来源、版本固定策略、漏洞更新和供应链风险。
6. 日志不得打印明文密码、Token、私钥或包含秘密的完整连接串。
7. 数据库和其他有状态服务的卷不能被普通 `clean` 操作隐式删除。
8. 对破坏性命令采用显式参数或单独目标，并在执行前显示将影响的资源。

## 7. 服务健康与 readiness

团队需要区分：

- 进程存在；
- 容器运行；
- 容器自身 healthcheck 通过；
- 业务所需能力真正就绪。

针对不同服务使用不同检查：

- MySQL：用预期账号建立连接并执行轻量 SQL，必要时验证目标数据库存在。
- Redis：用预期连接配置执行 `PING` 或合适的读写探测。
- HTTP 服务：检查健康端点的状态码及必要响应字段。
- 依赖型服务：验证关键下游依赖就绪，再允许后续阶段继续。

所有 readiness 检查都应有超时上限、明确退出码和可理解的失败原因。TCP 端口可连通只能证明网络层面可达，不等于数据库认证和业务能力可用。

## 8. 测试与质量门禁

建议分层实施：

1. **静态检查：** 格式、配置语法、敏感信息扫描、脚本 lint（如适用）。
2. **单元测试：** 验证局部逻辑及错误分支。
3. **集成测试：** 验证应用与 MySQL、Redis、Nacos 等依赖之间的交互。
4. **端到端测试：** 从统一入口完成构建、测试和部署后验证。
5. **故障注入：** 模拟服务未就绪、错误凭据、超时、构建失败和部署中断。
6. **恢复测试：** 验证重试、重新执行、恢复旧版本和数据保护流程。

测试报告至少记录：命令、环境、预期结果、实际结果、退出码、执行时间和失败日志。没有执行的测试应明确写“未执行”，不得标为通过。

## 9. 日志与流水线可观测性

每次流水线运行建议生成唯一 `run_id`，并记录：

- 源码 commit、分支和触发原因。
- 开始 / 结束时间与总耗时。
- 每一阶段的状态、退出码和日志位置。
- 测试报告、制品路径、镜像 tag / digest。
- 部署目标、部署版本和健康检查结果。
- 失败阶段、失败原因、是否可重试及恢复结果。

日志需要有保留期限和清理策略；清理日志不得误删重要审计记录。结构化数据宜使用稳定字段名，避免仅依赖人类可读的长文本。

## 10. 重试、幂等、检查点与恢复

1. 把错误分类为可重试、不可重试和需人工处理。
2. 重试要有限次、有超时，并采用退避策略；避免无限循环。
3. 重试前确认副作用：例如数据库写入、迁移、发消息和部署并不天然安全可重试。
4. 对非幂等动作使用幂等键、去重记录、事务、补偿步骤或人工确认。
5. 对多阶段流水线持久化阶段状态，恢复时先判断已完成步骤和产物是否仍有效。
6. 对部署保留上一可用版本的识别与回滚方法。
7. 对有状态数据先定义备份与恢复演练，再将自动清理纳入流水线。

## 11. 前端发布与制品管理

- 确认 `plus-ui` 的实际构建命令、输出目录和环境配置；不可只假设 `dist/` 位于某路径。
- 发布前检查构建是否成功、必要文件是否存在、目标目录是否正确。
- 明确静态资源缓存策略；带 hash 的静态资源和入口 HTML 可能需要不同缓存时间。
- 发布后验证 HTTP 状态、关键资源和浏览器运行路径。
- 推荐以版本目录或不可变制品进行发布，避免直接覆盖唯一可用版本。
- 镜像与制品标识应关联源码 commit；正式记录优先保存镜像 digest，而非仅使用可变标签。

## 12. Agent Runtime 扩展规范

Agent 执行代码或调用工具前，应逐步具备以下能力：

- **权限边界：** 文件系统、命令、网络、秘密和外部服务权限最小化。
- **隔离执行：** 使用有资源限制、可清理、可观测的独立工作环境。
- **前置约束：** 定义输入格式、允许工具、禁止操作和完成条件。
- **执行循环：** 计划、调用工具、观察结果、验证、决定继续或终止。
- **验证传感器：** 单测、构建结果、静态检查、服务健康和输出契约共同验证结果。
- **任务状态：** 明确状态转换、超时、取消和中断语义。
- **跨会话记忆：** 只保存经过筛选的任务事实、决策和经验；记录来源、时间、适用范围与置信度，支持修正与失效。
- **审计轨迹：** 能追踪谁/哪个 Agent 在何时以什么权限调用了什么工具，以及验证结果。
- **人工介入：** 对删除数据、公开发布、权限提升和不可逆操作设置人工确认门槛。

先完成基础开发流水线，再引入 Agent 自主执行。不要在缺少隔离、审计和恢复机制时给 Agent 默认的宿主机高权限。

## 13. 架构决策记录（ADR）

当决策影响后续维护、团队接口或安全边界时，应写一份 ADR，包括：

- 标题与日期；
- 背景和问题；
- 候选方案；
- 决策及理由；
- 代价、风险和替代方案；
- 复查触发条件。

示例主题：为何选择某种 readiness 检查、Nginx 使用何种网络模式、制品如何版本化、是否采用本地 CI runner。

## 16. 最低完成定义（Definition of Done）

除非任务明确说明不适用，任务只有满足以下条件才可关闭：

- [ ] 目标和验收标准已满足。
- [ ] 相关测试已执行并通过，未执行项有明确说明。
- [ ] 错误路径、超时和退出码符合约定。
- [ ] 安全、配置与数据副作用已检查。
- [ ] 日志和诊断信息足以排查问题。
- [ ] 文档、配置样例和任务状态已更新。
- [ ] 变更已审查；需要时已记录 ADR。
- [ ] 回滚 / 恢复步骤已验证，或明确说明尚未验证的风险。

## 17. 初始采用建议

本文件是团队协作的起点，不代表当前仓库已经实现这里列出的全部能力。建议先以轻量方式采用：

1. 立即采用 Git、安全、任务状态和验收证据规范。
2. 优先解决仓库路径歧义、MySQL readiness、环境变量缺失和脚本错误传播。
3. 逐步补齐测试报告、制品追踪、发布回滚与故障注入。
4. 待基础流水线稳定后，再把 Agent 沙箱、检查点和长期记忆纳入实施。
