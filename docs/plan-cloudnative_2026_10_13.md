# 今日工作计划 · RuoYi-Cloud-Plus 云原生改造探索

> 日期：2026-10-13（周二）
> 目标：**验证"基础设施容器化 + 应用本地开发"混合模式的可行性**，为项目云原生改造探路
> 定位：改造方案的第一阶段验证，非最终形态

---

## 一、背景

RuoYi-Cloud-Plus 是微服务架构（12 个服务模块），当前为传统本地部署：
数据库、缓存、注册中心各自安装配置，环境一致性差、新成员上手成本高。

本项目计划向**容器化部署 + DevOps 平台**演进。为控制风险，采用**分阶段推进**，
今日完成第一阶段的可行性验证。

## 二、今日方案

采用**混合部署**模式，兼顾两端优势：

| 层级 | 运行位置 | 方式 | 收益 |
|---|---|---|---|
| **基础服务**<br>MySQL / Redis / Nacos | WSL + Docker | 容器化 | 环境标准化，一次配置全组复用，可整体销毁重建 |
| **应用服务**<br>Gateway / Auth / System | Windows + IDEA | 本地启动 | 保留断点调试、热部署等开发体验 |

**为什么这样分**：基础设施变更频率低、配置项多、最需要一致性，适合容器化；
应用服务处于高频开发调试阶段，留在 IDE 中效率最高。
这一划分让团队**在不牺牲开发效率的前提下，先拿到容器化的收益**。

## 三、今日任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | **搭建容器化基础环境** | 在 WSL 中用 Docker 部署 MySQL、Redis、Nacos 三件套，统一网络配置与数据持久化目录 |
| 2 | **导入配置中心数据** | 将 12 个服务模块的配置文件导入 Nacos，实现配置集中管理 |
| 3 | **启动核心应用服务** | 在 IDEA 中启动 Gateway、Auth、System 三个核心服务 |
| 4 | **验证跨环境链路** | 验证应用服务能否成功注册到容器化的注册中心，并打通服务间调用 |

## 四、预期成果

今日结束时，应达成以下条件：

- [ ] 三个基础服务以容器方式稳定运行，支持一键启停与重建
- [ ] 服务配置集中托管于 Nacos，不再散落于各模块配置文件
- [ ] Gateway / Auth / System 在 IDEA 中正常启动，**成功注册到容器化注册中心**
- [ ] 跨环境服务调用链路打通（Windows 应用 ↔ WSL 容器）
- [ ] 输出一份可复现的环境搭建说明

**其中第 3、4 项是本次验证的核心**——若跨环境链路不通，混合模式即不可行，需调整方案。

## 五、关键技术决策

今日验证中需要确认的一个关键点：

> **跨平台网络互通**。WSL 与 Windows 属于不同的网络环境，
> 容器若沿用原有配置，Windows 侧的应用服务将无法访问容器中的注册中心。

经前期实测：**采用端口映射方式可解决此问题**（已通过验证）。
今日将在真实环境中完整验证该方案，并固化配置。

这一点也是后续向 Kubernetes 迁移时必须解决的共性问题，
本次验证的结论可直接复用。

## 六、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 跨环境网络不通 | 应用无法连接注册中心，验证失败 | 已通过前期实测确认可行方案；若仍异常，回退到"应用也容器化"的备选路径 |
| 服务注册地址错误 | 服务虽启动但相互调用失败 | 显式指定服务对外注册地址 |
| 配置中心数据缺失 | 服务启动报错 | 已梳理全部配置文件清单，逐项核对 |

## 七、后续演进路径

今日验证通过后，按三阶段推进云原生改造：

| 阶段 | 内容 | 目标 |
|---|---|---|
| **一（今日）** | 基础设施容器化，应用本地运行 | 验证混合模式可行性，统一基础环境 |
| **二** | 应用服务容器化，全链路容器部署 | 打通镜像构建与编排，形成可交付的部署包 |
| **三** | 健康检查、故障自愈、CI 流水线 | 具备上 DevOps 平台的条件 |

当前重点：完成第一阶段验证，为第二阶段的全量容器化积累经验与配置资产。
