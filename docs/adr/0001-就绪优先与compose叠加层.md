# ADR-0001：就绪优先，且用叠加层而非改原 compose

- 日期：2026-10-10
- 状态：已实施（待冷启动验收）
- 决策者：bvh-gif

## 背景与问题

原 `script/docker/docker-compose.yml` 里 `healthcheck` 数量 0、`restart` 数量 0，业务服务没有 `depends_on`。
团队同时想推进「把 host 网络迁到 bridge 网络」。两件事撞在一起，需要决定先做哪个、怎么做。

## 决策一：先补就绪信号，再改网络拓扑

**决策**：先做 MySQL/Redis/Nacos 的就绪检查与依赖编排，host → bridge 迁移作为独立任务后置。

**理由**
1. 迁移网络后如果服务起不来，**当前没有任何手段判断是网络问题还是服务问题**。没有验证手段就改架构，违反本项目规范原则 2（先可靠、可验证、可恢复，再追求更复杂的自动化）。
2. 网络迁移的收益主要是安全隔离与可重复性，**与服务发现无关**——Nacos 已经承担服务发现，且与应用层无关，改网络不会让它"更可用"。
3. 就绪检查本身是后续所有自动化（流水线、失败重试、恢复）的判定基准，属于前置依赖。

**代价**
- 推迟了安全隔离收益（`privileged: true` + `network_mode: host` 仍然存在于 28 个 service）。

**替代方案**
- 直接先迁网络：更快拿到隔离性，但失败时无法定位，且回滚成本高。**未采纳**，原因见理由 1。

## 决策二：用叠加层（overlay），不改 `docker-compose.yml`

**决策**：新增 `docker-compose.health.yml`，通过 `-f` 叠加使用。

**理由**
1. 本项目工作流是「个人 Fork 跟随官方 upstream」，改上游文件会在每次同步时产生冲突。
2. 健康检查/重启策略属于**本地运维策略**，与"应用在跑什么"（镜像、端口）应当分离。
3. 想退回原始行为，去掉第二个 `-f` 即可，无需 `git checkout` 恢复文件。

**代价**
- 叠加层**不会自动生效**（只有名为 `docker-compose.override.yml` 的文件才会），忘记加 `-f` 会导致健康检查全部缺失**且不报错**——这是静默失效，是本方案最大的风险。
- 配置分散后，`docker compose config` 成为唯一真相来源，必须养成查看习惯。
- 合并语义非直觉：映射型字段按键合并（后者胜）、`ports` 追加、其它列表（`command`、`healthcheck.test`）**整体替换**。

**替代方案**
- 改名为 `docker-compose.override.yml` 以自动加载：省掉 `-f` 参数，但引入**隐式行为**，接手的人看不到配置从哪来。**未采纳**——显式失败优于隐式生效。
- 直接改原文件：最简单，但每次同步上游都要解冲突。**未采纳**。

**缓解措施**
- 文件名保持显式，并在文件头部注释里写明用法与 `$$` 转义规则。
- 交付物中提供 `readiness.sh` 作为可独立运行的验证入口，即使忘记 `-f` 也能发现依赖没就绪。

## 复查触发条件

- 出现第二套环境（如测试环境）需要差异化配置时 → 重新评估是否改为按环境的 `-f` 拆分。
- 叠加层超过 3 层 → 应重构为独立的 compose 项目。
- 上游 `docker-compose.yml` 结构体发生较大变更 → 重新跑 `config -q` 校验合并结果。
